# split-check-bot

Для сравнения **уже сохранённых JSON без запуска OCR** используйте
`python -m tools.evaluate_receipt` — [инструкция](#офлайн-оценка-json-чеков).

Для сравнения качества OCR на собственных чеках доступен отдельный
`python -m tests.receipt_benchmark`. Формат эталонов, безопасные примеры,
метрики и сохранение отладочных изображений описаны в
[инструкции benchmark](tests/fixtures/receipts/README.md).

Telegram-бот для разделения общего чека между друзьями. `/start` открывает меню;
«🧾 Разделить чек» предлагает фотографию или ручной ввод. Позиции с фотографии
сохраняются в текущий чек только после подтверждения пользователем.
После подтверждения фото или завершения ручного ввода доступно распределение
позиций, учёт фактических оплат и расчёт переводов между участниками.
Сохранение компаний и выполнение банковских переводов пока не реализованы.

Основное распознавание — **OpenRouter Nemotron Vision**:
`nvidia/nemotron-3.5-super-vl:free`. Оригинальное изображение отправляется
напрямую через HTTP, без предварительного OCR и OpenAI SDK.
Резервный backend — локальный **Tesseract rus+eng**, `pytesseract` и Pillow/OpenCV.
PaddleOCR, Gemini и `OPENAI_API_KEY` не используются. Доступность бесплатного
провайдера и его лимиты зависят от OpenRouter; платного переключения нет.

## Установка и запуск

Используются Python 3.12 и aiogram 3.x. В Debian/Ubuntu сначала выполните
однократную подготовку среды из корня проекта:

```bash
sh scripts/install_tesseract.sh
```

Скрипт запускает через root/sudo `apt-get update` и устанавливает системные пакеты
`tesseract-ocr`, `tesseract-ocr-rus`, `tesseract-ocr-eng`, затем проверяет языки.
Если sudo отсутствует, запустите скрипт от root или попросите администратора
подготовить среду. Бот никогда не вызывает установку пакетов.
При установке нужен доступ к репозиторию пакетов; сетевые настройки скрипт
не меняет. Данные языков устанавливаются заранее вместе с пакетами.

Проверка установки:

```bash
tesseract --version
tesseract --list-langs
```

В списке должны быть **оба** языка: `rus` и `eng`. Одного `pip install pytesseract`
недостаточно: это Python-обёртка, системный executable устанавливается отдельно.
В другой ОС установите локальный Tesseract с русскими и английскими данными
и добавьте `tesseract` в `PATH`.

Установите Python-зависимости:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В Windows можно использовать `py -3.12 -m venv .venv`,
`.venv\Scripts\Activate.ps1` и `Copy-Item .env.example .env`.

Создайте бота через [@BotFather](https://t.me/BotFather) командой `/newbot`.
Заполните в `.env` токен и запустите:

```dotenv
BOT_TOKEN=ваш_токен_от_BotFather
OPENROUTER_API_KEY=ваш_ключ_OpenRouter
RECEIPT_OCR_BACKEND=openrouter
OPENROUTER_RECEIPT_MODEL=nvidia/nemotron-3.5-super-vl:free
```

```bash
python -m bot
```

`.env` исключён из Git. Уже заданные переменные окружения имеют приоритет.
`RECEIPT_OCR_BACKEND` можно не задавать: `openrouter` используется по умолчанию.
Для полностью локальной работы задайте `RECEIPT_OCR_BACKEND=tesseract`.
При обновлении старой среды замените ранее заданное значение `tesseract` на
`openrouter`: уже заданные переменные имеют приоритет над `.env`.
Ключ храните в секретах среды или игнорируемом `.env`, не в Git.
`OPENROUTER_RECEIPT_MODEL` опционален: допускается только точный ID выше.
Другие модели, включая платный ID без `:free`, отклоняются; суффикс никогда не удаляется.
OpenRouter получает `provider.allow_fallbacks=false`, список запасных моделей
не передаётся. Если ключ отсутствует или конфигурация модели невалидна,
используется локальный резервный backend.
Старые значения `paddleocr` и `openai` больше не поддерживаются; при обновлении
удалите их из настроек или замените на `openrouter` либо `tesseract`.
При нестандартном расположении заранее установленных языков можно задать
`TESSDATA_PREFIX` в окружении или `.env`: путь к каталогу с `rus.traineddata`
и `eng.traineddata`. Он должен содержать оба файла. Данные автоматически
не загружаются ни при запуске бота, ни при распознавании.

Откройте бота в Telegram и отправьте `/start`. Для остановки нажмите `Ctrl+C`.
Нужен доступ к `api.telegram.org` и `openrouter.ai`. HTTP-клиент OpenRouter
использует настроенный HTTPS-прокси и системное доверие TLS.
Запускайте один экземпляр long polling
с одним токеном; у бота не должен быть активен webhook.

## Распознавание фотографии чека

Путь по умолчанию: **Telegram photo → OpenRouter Nemotron → RecognizedReceipt →
существующий редактор → подтверждение пользователем**. После загрузки фото бот
пишет «Чек получен 🧾 Анализирую позиции…» и ожидает результат без промежуточного
спама. На OpenRouter отведено суммарно 180 секунд: подключение до 15 секунд,
чтение body до 180 секунд в пределах общего бюджета. Допускается не более одного
повтора после 5xx или ошибки соединения; тайм-ауты не повторяются. После 429, ошибки авторизации,
недоступного free-провайдера, тайм-аута, невалидного/обрезанного JSON или пустого
результата бот один раз пишет «Основное распознавание временно недоступно,
пробую резервный способ…» и передаёт исходные байты Tesseract.

Reasoning явно отключён через `reasoning.enabled=false`. Ответ ограничен строгой
JSON Schema из существующей `VisionReceipt`: nullable-поля, включая
`currency_evidence`, сохраняются; неизвестные значения передаются как `null`.
Локальная Pydantic-валидация выполняется до создания `RecognizedReceipt`.
Логи содержат HTTP status, время, finish reason, usage, количества и суммы.
Ошибки JSON и schema различаются; ошибки schema показывают путь и тип поля,
без входного значения. Неизвестные имена полей скрываются как `[extra]`.
Названия позиций и upstream error messages в логи не записываются.

Проверенный benchmark prompt требует структурированные позиции и отдельные
`gross_total`, `prepayment`, `amount_due`, `currency`. Количества и деньги
принимаются десятичными строками и считаются через `Decimal`. Повторяющиеся
товары и гости сохраняются. `uncertain=true` превращается в `suspicious` и
отображается как ⚠️. Строки с нечитаемым названием, количеством или суммой
пропускаются с предупреждением; значения не достраиваются. Неуказанная цена
за единицу остаётся `null`. Модельные названия, включая `Open Bar`, не переводятся
и могут быть исправлены в редакторе.

Явно указанная валюта сохраняется. При `currency=null` RUB устанавливается
только при признаке рубля либо сочетании кириллических названий, десятичных
итогов и российского ИНН в дополнительном `currency_evidence`, прочитанном
моделью с изображения. Одних кириллических названий недостаточно: без признаков
валюты сохраняется `null`, USD по умолчанию не подставляется. RUB отображается ₽.
Ключ, base64 и upstream-ответы не попадают в логи. Изображение backend хранит
только в памяти на время запроса. Полного OCR-текста у AI-backend нет;
кнопка его просмотра работает только для результата локального OCR.

### Локальный резервный Tesseract

Длинные узкие чеки (высота/ширина от 2.5 после геометрии и ориентации)
распознаются двумя стратегиями: весь чек и последовательные сегменты из
исходного разрешения с overlap около 12%. Выбирается результат с лучшей
структурой текста/цен/итогов и меньшим количеством мусора; при равенстве
остаётся полный проход. Parser позиций от стратегии не меняется. Длинный
чек может обрабатываться около 1–2 минут. Сравнение стратегий и метрики
описаны в [benchmark README](tests/fixtures/receipts/README.md).

Ресторанные чеки с гостями поддерживают подытоги гостей, полную сумму,
предоплату и остаток к оплате. Гость, стол, заказ, официант, заголовки таблицы
и платёжные строки не считаются товарами. Позиции сохраняют номер гостя.
Товары сравниваются с полной суммой; отдельно проверяются сумма подытогов
гостей и равенство «полная сумма − предоплата = к оплате».
Повреждённые итоговые числа не восстанавливаются догадками. Сомнительные
позиции пропускаются с предупреждением; сырой OCR-текст остаётся доступен.
Предоплата проверяется по полной сумме и остатку. При конфликте исходное
OCR-значение сохраняется как сомнительное и не участвует в расчётах; разница
итогов не подставляется вместо него. Без полной суммы такая проверка невозможна:
предоплата помечается непроверенной и не используется для вычисления gross.
USD требует явного поля валюты или надёжного обозначения в ценах/итоге;
случайный `$` в русском чеке, QR, URL и служебных данных не меняет RUB.

Архитектура локального резерва: **фото → подготовка Pillow → Tesseract → receipt parser → проверка
и подтверждение пользователем**.

Бот скачивает наибольший вариант Telegram-фотографии в `BytesIO`. Допускаются
файлы до 10 МиБ и изображения до 25 мегапикселей. Подготовка учитывает поворот
по EXIF, ищет границы светлой бумаги и при уверенном обнаружении обрезает фон
и выравнивает перспективу. При неопределённых границах сохраняется весь кадр.
Небольшой наклон исправляется по горизонтальным проекциям без обрезки краёв.
Grayscale увеличивается в 2–3 раза с пределом 3600 пикселей по длинной стороне;
применяются выравнивание теней, мягкий CLAHE-контраст, лёгкое удаление шума
и sharpening. Эрозия букв не используется. Уверенный результат Tesseract OSD
позволяет исправить поворот на 90/180/270°; при недоступном `osd` или недостатке
текста сохраняется ориентация по EXIF.

Сравниваются grayscale и adaptive Gaussian threshold с PSM **6, 4, 11**.
Grayscale остаётся отдельным кандидатом на случай потери тонких штрихов
при бинаризации. Оценка использует количество уверенных букв/цифр и целых
денежных значений; число разрозненных блоков PSM 11 не повышает оценку.
Такие блоки собираются в строки по координатам слов. Один `image_to_data`
возвращает текст и confidence каждого варианта. Язык — `rus+eng`, тайм-аут
до 12 секунд на конфигурацию, общий бюджет сравнения — 45 секунд, плюс до
5 секунд на OSD. Ошибка отдельного варианта не теряет успешные результаты.
Перед OCR проверяются executable и оба языка: отсутствие русского не приводит
к незаметному переходу на один английский. Распознавание выполняется в отдельном
рабочем потоке и не блокирует event loop бота.

До parser проверяются минимум три строки с уверенным текстом, шесть уверенных
слов/чисел и доля уверенных токенов. Слишком скудный или низкоуверенный текст
не превращается в позиции: бот предлагает переснять чек ближе, ровнее и без
теней. Сырой текст остаётся доступен по кнопке «📄 Показать распознанный текст».
Очень короткий чек тоже может потребовать ручного ввода. Выбранная обработка,
PSM, количество строк и оценка пишутся только в developer log; текст чека,
байты изображения и технические параметры в пользовательский ответ не попадают.

Существующий parser сохранён. Он поддерживает название с суммой справа,
количество × цену, колонки количество/цена/сумма и название на строке перед ценой.
Деньги разбираются и считаются через `Decimal`, без `float`; при сериализации
в FSM используются десятичные строки. Поддерживаются точка, запятая и пробелы
тысяч. Извлекаются название, количество, цена за единицу, сумма строки и итог
чека. Неизвестная цена за единицу остаётся `null`; если виден только итог строки,
количество предварительно считается равным одному.

Фискальные строки, дата/время, оплата, НДС и скидки отфильтровываются.
«ИТОГО» извлекается отдельно. Валюта по умолчанию RUB; обозначения USD/EUR
учитываются. Parser эвристический: сложная вёрстка и ошибки OCR могут дать
неполный список. Бот показывает найденные позиции, их сумму и итог чека,
если он найден, и предупреждает о расхождении сумм.

Кнопки проверки:

- «✅ Всё верно» — переносит позиции в текущий чек в FSM;
- «✏️ Исправить» — выбор позиции, изменение названия/количества/цены и удаление с подтверждением;
- «➕ Добавить позицию» — ручное добавление в текущий распознанный чек;
- «🔄 Распознать заново» — повторно скачивает последнюю фотографию и выполняет OCR;
- «📄 Показать распознанный текст» — показывает сырой текст без изменения чека;
- «❌ Отменить» — очищает состояние и возвращает стартовое меню.

Если OCR прочитал текст, но parser не выделил позиции, бот сразу показывает
сырой текст и предлагает ручной ввод, повторное распознавание или отмену.
Пустой результат, отсутствие Tesseract/языков и ошибки OCR также позволяют
отправить новое фото или перейти к ручному вводу. Внешнего fallback нет.

Фото вне сценария получает подсказку с кнопкой начала разделения чека.
Во время ручного ввода фотография не сбрасывает шаг и добавленные позиции.
Фото и распознанный текст не логируются. `pytesseract` использует временные файлы
на время вызова системного executable и удаляет их после обработки.
Фотографии не сохраняются на диск. Подтверждённые структурированные чеки и
расчёты хранятся в локальной SQLite (см. «Сохранённые чеки и восстановление»).
В FSM до подтверждения остаются результат, сырой текст и Telegram-метаданные
фото. После подтверждения сырой текст и метаданные удаляются. Новый чек,
ручной ввод, отмена, `/start` и перезапуск очищают соответствующие данные.

## Диагностика OCR и запуска

При запуске бот пишет в developer log используемый Python, backend, версию
`pytesseract`, путь к Tesseract, `TESSDATA_PREFIX`, версию системного Tesseract
и доступные языки. Проверка выполняется в процессе бота после загрузки `.env`.
Если OCR не готов, в логе остаётся traceback; ручной ввод продолжает работать.

Ошибки распознавания записываются с полным traceback и исходной причиной,
включая сообщение/код ошибки Tesseract. Байты фотографии и полный OCR-текст
отдельно в лог не передаются. В Telegram пользователь получает понятное
сообщение и кнопки повтора, ручного ввода и отмены, без технических деталей.
Длинные traceback находятся в stderr процесса; сохраняйте его при запуске.

`TelegramConflictError: terminated by other getUpdates request` означает,
что тот же токен использует другой экземпляр long polling. Сначала остановите
предыдущий процесс (включая другие облачные задачи), затем запускайте новый.
Это ошибка получения обновлений Telegram, а не ошибка Tesseract.

При обновлении работающего экземпляра сверяйте checkout с `origin/main`:

```bash
git fetch origin main
git merge --ff-only origin/main
python -m pip install -r requirements.txt
python -m pip check
```

После проверки тестов остановите старый процесс и запустите бота заново
тем же Python, с теми же `BOT_TOKEN` и `TESSDATA_PREFIX`. Уже работающий Python
не подхватывает обновлённые модули автоматически. Установка Tesseract сама
по себе не меняет backend старого checkout: версия `7156c5f` использует только
OpenAI и без `OPENAI_API_KEY` отвечает «Распознавание пока не настроено».
В актуальном checkout Tesseract используется как резерв; проверьте в логе
нового процесса выбранный backend (`openrouter` по умолчанию) и наличие
`rus` и `eng` для локального резерва.

## Ручной ввод чека

Нажмите «🧾 Разделить чек» → «✍️ Ввести вручную». Бот последовательно спросит
название позиции, цену в рублях и количество. Цена должна быть больше нуля;
поддерживаются целые числа и дробные числа с точкой или запятой.
Количество — целое число больше нуля. При ошибке бот повторяет текущий шаг.

После добавления бот показывает список позиций, стоимость каждой позиции
(цена × количество) и общую сумму. «➕ Добавить позицию» запускает следующий
ввод, «✅ Закончить ввод» показывает итог и завершает сценарий,
«❌ Отменить» очищает чек и возвращает стартовое меню. `/start` также сбрасывает
текущий ввод. Расчёты используют `Decimal` без ошибок округления `float`.

Чеки и состояние FSM хранятся в оперативной памяти отдельно для каждого
пользователя и чата. Завершение ручного ввода сохраняет чек для делёжки.
Подтверждённый чек и распределение остаются до нового чека, отмены, `/start`
или перезапуска; постоянного хранения и базы данных пока нет.

## Распределение расходов

После «✅ Всё верно» или «✅ Закончить ввод» нажмите «👥 Распределить расходы».
Добавьте участников по одному: непустое уникальное имя до 60 символов,
до 30 участников в чеке. Затем откройте «🧾 Назначить позиции», выберите строку,
отметьте одного или нескольких участников и сохраните назначение. Повторяющиеся
позиции остаются отдельными строками с номерами; гость из исходного чека
сохраняется как справочная информация, без автоматического назначения.

Распределение работает в одном интерактивном сообщении: галочки, сохранение,
возврат, списки блюд и итоги обновляют этот экран без новых сообщений.
В карточке блюда есть «Предыдущее блюдо» и «Следующее блюдо»; переход сохраняет
текущий выбор. «Сохранить назначение» сохраняет его и возвращает к списку,
а «Назад без сохранения» отменяет только несохранённые изменения текущего блюда.
Нумерация, названия, количества, суммы, гости и уже назначенные участники сохраняются.
Длинные тексты листаются кнопками внутри того же сообщения, без потери данных.

Каждая строка делится поровну в целых копейках. Например, 0.05 на троих даёт
0.02 + 0.02 + 0.01. Остаток получают первые выбранные участники в порядке
добавления. Сумма долей всегда совпадает с суммой строки; расчёт использует
`Decimal` и целые копейки, без `float`. Ручные суммы с долями копейки не
округляются незаметно: переход сообщает о необходимости проверить ввод.

Предварительный итог показывает доли каждого участника и все неназначенные
строки. Завершить распределение можно только после назначения всех позиций.
Назначение можно снять, а завершённый результат — снова открыть для изменения.
Несовпадение суммы строк с общей суммой чека явно показывается и в итоговом
результате; недостающие строки и корректировки сумм автоматически не создаются.
Доли рассчитаны по позициям; предоплата и остаток к оплате показываются отдельно.
Оплаты участников вводятся явно после завершения распределения.

Распределение ведёт один пользователь в своём FSM-контексте чата: это список
участников для расчёта, а не совместное редактирование несколькими Telegram-аккаунтами.
Токен чека, версия меню и проверка владельца защищают от старых, повторных и чужих
нажатий. «Назад без сохранения» отменяет выбор текущей строки, «К чеку» сохраняет
распределение для продолжения. `/start` сбрасывает весь текущий чек.
Кнопки также привязаны к конкретному сообщению. Если Telegram не разрешает
обновить экран, действие откатывается и дубликат автоматически не отправляется.
Повторите действие или явно откройте новый экран командой `/allocation`:
сохранённое распределение и оплаты останутся, несохранённый выбор будет отменён.
`MessageNotModified` обрабатывается без ошибки и новых сообщений.

Проверки без сети: `python -m unittest tests.test_expense_split tests.test_handlers -v`
и `python -m unittest discover -s tests/integration -p test_expense_allocation_flow.py -v`.
Новый integration-сценарий использует настоящий aiogram Dispatcher/FSM,
подменяет OCR и Telegram-транспорт и запрещает вызовы AI API.

## Оплаты участников и переводы

После завершения распределения нажмите «💳 Оплаты и переводы». Для каждого
плательщика укажите общую сумму, фактически внесённую им в ресторан, включая
его предоплату. Неуказанная оплата считается нулевой; плательщиков может быть
несколько. Предоплата из OCR сама в оплаты не добавляется. Например, если один
участник внёс аванс 400, а другой оплатил оставшиеся 600, введите 400 и 600 —
не добавляйте аванс повторно к уже введённой полной оплате.

Нажмите имя участника и отправьте сумму обычным текстовым сообщением, без
«Ответить». Просьба ввести сумму, ошибки ввода и результаты показываются через
редактирование того же интерактивного экрана; отдельного `ForceReply` нет.
Принимаются точка или запятая и максимум два знака после неё; доли копейки,
отрицательные значения, экспоненциальная запись и `float` не используются.
Введённая сумма заменяет прежнюю, а не прибавляется к ней; `0` снимает оплату.
При ошибке суммы можно сразу отправить исправленное значение.
«Назад без сохранения» отменяет ввод и оставляет прежнее значение.

Ввод доступен только владельцу в том же чате и активном режиме выбранного
плательщика. Сессия привязана к чеку и версии экрана; сообщения с номерами
обновлений до открытия ввода, повторные сообщения и старые ответы на вопросы
бота игнорируются. Вне режима ввода обычное сообщение не меняет оплаты.
При ошибке редактирования экрана сумма и режим откатываются; повторная доставка
того же сообщения игнорируется, для новой попытки отправьте сумму ещё раз
новым сообщением. Суммы и имена не логируются. Ввод имён также остаётся
обычным текстом; inline-кнопки не заменяют текстовый ввод.

Кнопка «💰 Добавить чаевые» открывает ввод общей суммы обычным сообщением.
Положительная сумма остаётся черновиком до выбора одного плательщика чаевых.
Выбор сохраняет сумму и плательщика вместе. До него «Назад без сохранения»
отменяет весь ввод, сохраняя прежний расчёт. Неверную сумму можно ввести заново.
После сохранения доступны изменение суммы и отдельная смена плательщика;
`0` удаляет чаевые и их плательщика без дополнительного выбора.

Чаевые делятся поровну между всеми участниками в целых копейках. Неразделимые
копейки получают первые участники в порядке добавления, независимо от того,
кто оплатил чаевые. Они не меняют позиции, полную сумму чека, предоплату или
остаток. Экран показывает ресторанный счёт, чаевые и общие расходы отдельно.
Ресторанные оплаты вводите **без чаевых**: выбранный плательщик чаевых уже
учитывается отдельно на всю их сумму. В MVP плательщик чаевых только один.
Ввод, выбор плательщика и отмена редактируют тот же экран; проверки сессии,
владельца и повторных сообщений действуют и для чаевых. При отказе Telegram
изменение суммы/плательщика и FSM откатывается; для повтора текстового ввода
нужно отправить новое сообщение.

Баланс каждого участника равен «ресторанные оплаты + оплаченные им чаевые −
доля ресторанного счёта − доля чаевых»: положительный баланс
означает, что участнику должны вернуть деньги, отрицательный — что он должен
перевести. Переводы считаются в целых копейках, в стабильном порядке участников;
после выполнения предложенных переводов все балансы равны нулю. Когда каждый
уже оплатил свою долю, переводы не нужны. Переводы между участниками не следует
повторно вводить как оплаты в ресторан.

До «✅ Подтвердить расчёт переводов» список помечен как предварительный.
При несовпадении оплат с ресторанным счётом после скидки или конфликте с итогом чека
показываются предупреждения и балансы; список переводов не строится и его
подтверждение блокируется на сервере. Сверка ресторанных оплат выполняется
только со счётом после явно введённой скидки, без чаевых. Без выбранного плательщика положительных
чаевых подтверждение также блокируется. Распределение всех позиций также должно
быть завершено. Никакие суммы не дополняются или не исправляются автоматически.

Исправление ресторанной оплаты, скидки, чаевых или смена их плательщика
сбрасывает подтверждение. Возврат к изменению распределения
тоже сбрасывает его, сохраняя фактически внесённые оплаты: после нового
распределения балансы пересчитываются. Подтверждение означает согласование
расчёта, а не отправку денег. Все данные по-прежнему хранятся только в FSM
пользователя/чата и сбрасываются при `/start`, новом чеке или перезапуске.

Проверки: `python -m unittest tests.test_settlements tests.test_expense_split -v`
и `python -m unittest discover -s tests/integration -p test_expense_allocation_flow.py -v`.

Пример: доли ресторана 5130 / 4810 / 4300 ₽, ресторан 14240 ₽ оплатил
второй участник, чаевые 900 ₽ — третий. Общие доли: 5430 / 5110 / 4600 ₽;
балансы: −5430 / +9130 / −3700 ₽. Первый переводит второму 5430 ₽,
третий — второму 3700 ₽. Общие расходы — 15140 ₽.

## Общая скидка

После распределения в «💳 Оплаты и переводы» доступна кнопка «🏷️ Добавить скидку»
(«🏷️ Изменить скидку» после сохранения). Введите общую сумму обычным сообщением,
без ForceReply. Допустимы точка/запятая, не более двух знаков после неё,
значения от нуля до суммы позиций. `0` удаляет скидку; неверную сумму можно
ввести заново. «Назад без сохранения» оставляет прежнюю скидку и подтверждение.
Ввод и результат редактируют прежний экран. Проверки владельца, чата, режима,
версии экрана и ID событий действуют и здесь. При ошибке Telegram скидка и FSM
откатываются, но использованный ID сообщения не применяется повторно;
отправьте сумму новым сообщением для новой попытки.

`discount_amount` — отдельная строка Decimal, по умолчанию `0.00`, в том числе
при загрузке старого Allocation. Суммы позиций, `gross_total`, `prepayment`,
`amount_due`, `currency`, ресторанные оплаты и чаевые не переписываются.
Экран показывает сумму до скидки, скидку, ресторан после скидки, оплаты,
чаевые и общие расходы отдельно. Сохранение скидки сбрасывает подтверждение.

Сначала считаются прежние ресторанные доли по позициям (включая распределение
общих блюд и копеек). Скидка распределяется пропорционально этим долям методом
наибольших остатков: в целых копейках для каждой доли находятся целая часть и
остаток `скидка × доля / сумма долей`; оставшиеся копейки получают наибольшие
остатки, при равенстве — первые участники по порядку добавления. Произведения
и остатки считаются целыми числами без потери точности. Нулевая доля получает
нулевую скидку. Пересчёт всегда идёт от исходных долей, без накопления скидки.
Пока есть неназначенные позиции, делить скидку и подтверждать расчёт нельзя.
Чаевые по-прежнему делятся поровну между всеми участниками отдельно.

Ресторанные оплаты сверяются с `сумма позиций − скидка`; общие расходы равны
этой сумме плюс чаевые. Предоплата входит только в явно введённые оплаты и
повторно не добавляется к расходам.

Только положительная скидка, сохранённая пользователем, разрешает трактовать
напечатанный `gross_total` как сумму до **или** после скидки, если он точно
совпадает с одной из них. Скидка не вычисляется автоматически из разницы.
Сами факты OCR сохраняются. Различающиеся значения допустимы для точной пары:
`gross_total` равен сумме позиций до скидки, `receipt_total` — сумме после явно
введённой скидки. Например, 4600 и 3680 при скидке 920. Обратная пара и прочие
несогласованные итоги считаются неоднозначными и блокируют подтверждение.
Без ввода скидки такой случай не меняет ресторанную сумму автоматически.
Если есть предоплата и остаток,
их сумма должна равняться ресторану после скидки. Остаток без известной
предоплаты может совпадать только со всем счётом после скидки; разница не
превращается автоматически в предоплату. Предоплата не может превышать счёт.
Уже помеченная OCR как сомнительная предоплата остаётся сомнительной, её значение
не восстанавливается из карантина. При таких конфликтах экран предупреждает и
блокирует подтверждение. Без скидки сохраняется прежняя сверка с `gross_total`.

Пример: ресторанные доли 1000 / 2000 / 1600 ₽, скидка 920 ₽. Скидки участников:
200 / 400 / 320 ₽, итоговые доли: 800 / 1600 / 1280 ₽. Если второй участник
оплатил ресторан 3680 ₽, первый переводит ему 800 ₽, третий — 1280 ₽.
Если третий отдельно оплатил 300 ₽ чаевых, доли расходов становятся
900 / 1700 / 1380 ₽; балансы −900 / +1980 / −1080 ₽. Переводы второму:
900 и 1080 ₽, общие расходы 3980 ₽, сумма балансов нулевая.

Проверки без OCR/API: `python -m unittest tests.test_discounts -v`
и `python -m unittest discover -s tests/integration -p test_expense_allocation_flow.py -v`.

## Отображение валюты

Явное поле валюты OCR имеет приоритет, включая USD, EUR, KZT и другие валюты.
Когда оно пусто, отображение может подтвердить RUB по сохранённому тексту:
`₽` / `RUB` либо рублёвое обозначение с российскими признаками. Иностранные
или противоречивые обозначения блокируют такое подтверждение. Одна кириллица,
формат суммы и слово «рублей» без уточнения не делают неизвестную валюту RUB.
Обзор явно сообщает об источнике вывода; исходное поле `currency` не меняется,
а в распределение передаётся только признак подтверждения, без сырого текста.
Если свидетельства в результате распознавания отсутствуют, валюта остаётся
неопределённой. Запрос, prompt, schema и parser OCR для этого не менялись.

## Офлайн-оценка JSON чеков

Оценщик независим от бота: только стандартная библиотека Python, без токенов,
сети, OCR, изображений, изменений FSM или исходных JSON. Пример запуска:

```bash
python -m tools.evaluate_receipt --expected expected.json --actual actual.json
python -m tools.evaluate_receipt --expected expected.json --actual actual.json --format json
```

Оба JSON — объекты с `items`, где у строки есть `name`, `quantity`, `total_price`.
Например: `{"items":[{"name":"Синтетический чай","quantity":"2","total_price":"200.00"}],"gross_total":"200.00"}`.
Подходят прямой JSON модели и сохранённый `RecognizedReceipt`; оболочку HTTP
OpenRouter с `choices` предварительно извлеките самостоятельно. Опциональные
итоги `gross_total`, `prepayment`, `amount_due`, `receipt_total` сравниваются
отдельно и не выводятся друг из друга. В эталоне также принимаются существующие
поля `expected_items`, `expected_gross_total`, `expected_prepayment`,
`expected_amount_due`, `expected_total` (последнее означает `receipt_total`).
Одновременные алиасы одного поля отклоняются как неоднозначные.

Полное совпадение требует одинакового нормализованного названия **и** точного
равенства количества и суммы строки через Decimal. Нормализация названия:
Unicode NFKC, регистр, `ё` → `е`, пробелы; перевода, удаления пунктуации или
подмены названия нет. Деньги не округляются, отсутствующая сумма не вычисляется
из количества/цены. Поддерживаются нули, знаковые значения, дробные количества;
JSON-числа читаются сразу как Decimal. Некорректный эталон отклоняется, а
незаполненные/неверные поля строк OCR остаются в количестве распознанных строк
и диагностируются. Если хотя бы одна сумма строки OCR неизвестна, итоговая
сумма помечается неполной; отдельно показывается сумма известных значений.

Сначала резервируются полные совпадения. Оставшиеся строки сопоставляются
глобально один к одному: приоритет одинаковых названий, затем совпавших полей,
числа пар и сходства названий. Кандидаты — одинаковые названия, сходство не ниже
0.80 или уникальная среди оставшихся строк пара «количество + сумма».
Близкое/неверное название никогда не даёт полного совпадения. Частичная пара —
диагностическая гипотеза с указанным основанием, особенно при совпадении только
чисел; неоднозначные числовые совпадения не связываются. Порядок строк не влияет
на полные совпадения, каждая повторяющаяся позиция расходуется только один раз.
Эта строгая метрика отличается от старого OCR benchmark, допускающего неточность
названий в `found`; старый benchmark и его запуск не изменены.

Отчёт показывает полные/частичные пары, пропуски, лишние строки и ошибки
`name`/`quantity`/`total_price` **по номерам позиций с 1**, без значений исходных
строк. Также доступны числа совпавших полей среди сопоставленных пар, суммы
строк, разница `OCR − эталон`, разница gross и суммы строк, сравнение каждого
заданного итога. Отсутствующий эталонный итог имеет статус `not_provided`,
а не «совпало». Названия, гости, телефоны, адреса, сырой OCR-текст, изображения
и произвольные метаданные не копируются в отчёты или ошибки. Денежные итоги
выводятся; имена файлов/пути не выводятся. Автосохранения отчётов и логов нет.
Храните собственные JSON вне Git или в игнорируемой `work/`.

Код выхода: `0` — отчёт построен; `2` — ошибка JSON/формата/чтения. Опция
`--fail-on-difference` возвращает `1`, если обнаружены расхождения. Лимиты:
200 строк, 200 символов в названии, файл до 2 MiB, десятичные значения до 30 цифр
перед точкой и 12 после неё. Запятые, строки с экспонентой и нечисловые значения
не исправляются автоматически. Повторяющиеся JSON-ключи отклоняются.

[Восемь синтетических пар](tests/fixtures/evaluation/README.md) включают длинный
чек на 32 позиции. Проверки без внешних сервисов:

```bash
python -m unittest tests.test_evaluate_receipt -v
python -m unittest discover -s tests/integration -p test_receipt_evaluator_cli.py -v
```

## Тесты

Unit-тесты не запускают Tesseract и не требуют его установки. Подменяются
результат OCR, проверка языков и Telegram; настоящие Pillow/OpenCV проверяют подготовку
изображений. Сохранены тесты parser и сценарии ручного ввода. Дополнительно
проверяются отсутствие executable/языков, тайм-аут, сырой текст при ошибке parser,
подтверждение и повтор. OpenRouter подменяется: unit-тесты не обращаются
к внешнему API даже при настроенном ключе. Проверяются 32 позиции, Decimal,
дубликаты, гости, валюта, uncertain, ограничения модели, ошибки HTTP/JSON,
тайм-аут и переход на Tesseract, а также AI → редактор → подтверждение.
Нативные интеграционные тесты явно выбирают `tesseract`, независимо от настроек
основного backend, и не отправляют фото во внешние API.

```bash
python -m unittest discover -s tests -v
```

Отдельный integration/smoke-тест запускает настоящий Tesseract на синтетическом
PNG-чеке с русским и английским текстом через dispatcher и photo handler,
без `OPENAI_API_KEY`, с явно выбранным `tesseract` backend. Затем он проверяет состояние
проверки чека, текст ответа, позиции и `Decimal`-сумму:

```bash
python -m unittest discover -s tests/integration -v
```

Он пропускается, если Tesseract или `rus+eng` недоступны. Для кириллицы нужен
шрифт DejaVu Sans; при другом расположении задайте `TESSERACT_SMOKE_FONT`
путём к TTF со шрифтом, поддерживающим кириллицу.
Тесты не используют сеть, внешние OCR API или настоящие Telegram-токены.

Для дополнительного smoke test на настоящей фотографии с перспективой задайте
`RECEIPT_SMOKE_PHOTO` путём к `sample_images/receipt.jpg` из публичного проекта
[doc_scanner](https://github.com/andrewdcampbell/doc_scanner/blob/master/sample_images/receipt.jpg)
и повторите integration-команду. Тест проверяет обрезку/перспективу и текст
`BACON`, `FLOUR ALMOND`, `101.33` через обработчик фото с настоящим Tesseract.
Подменяется только Telegram-транспорт. Фотография не скачивается тестом
автоматически и не включена в репозиторий.

### Исправление распознанного чека

После OCR доступны «✅ Всё верно», «✏️ Исправить», «➕ Добавить позицию»,
повторное распознавание, просмотр исходного текста и отмена. В редакторе можно
выбрать товар, изменить название, количество или цену за единицу, удалить его
с подтверждением. Длинные списки показываются страницами по 20 позиций;
одинаковые товары остаются отдельными строками. ⚠️ отмечает исходные сомнительные
позиции; числовые confidence и параметры OCR в Telegram не выводятся.

Добавление использует существующие шаги ручного ввода — название, цена,
количество — и возвращает в текущий распознанный чек. В этом сценарии количество
может быть дробным (до 6 знаков), цена задаётся с точкой или запятой (до 2 знаков).
Расчёты выполняются через Decimal с округлением суммы строки до копеек
ROUND_HALF_UP. Если цена за единицу не была прочитана, изменение количества
применяется только после явного ввода цены; «Назад» отменяет незавершённое
изменение. Цена не выводится автоматически из старой суммы.

Редактор меняет только `recognition.items` текущего FSM. Исходные `raw_text`,
`gross_total`, `prepayment`, `amount_due` и подытоги гостей сохраняются.
Сумма товаров и предупреждение о её расхождении вычисляются заново при показе.
Удалённую последнюю позицию можно заменить новой; пустой чек подтвердить нельзя.
Новый standalone ручной чек по-прежнему использует прежний сценарий ввода.

Состояния находятся в `bot/receipt_states.py`, UI результата — в
`bot/receipt_view.py`, меню редактора и обработчики изменений — в
`bot/receipt_editor.py`. Основной router подключает редактор и направляет добавление
в существующие ручные шаги. Данные изолированы по пользователю/чату текущим FSM.
Подтверждённые чеки и расчёты дополнительно сохраняются в локальную SQLite
(см. ниже). Callback содержит короткий токен, версию меню и индекс;
устаревшая кнопка не редактирует сдвинувшуюся после удаления строку.

Unit-тесты редактора проходят через настоящий dispatcher со stub OCR, без
Tesseract. `tests/integration/test_receipt_editing_smoke.py` дополнительно проверяет
нативный локальный OCR → изменение цены → удаление → добавление → завершение →
подтверждение; подменяется только транспорт Telegram.


## Сохранённые чеки и восстановление

После подтверждения распознанного чека или завершения ручного ввода бот
автоматически сохраняет черновик в **локальную SQLite на сервере бота**.
Это не хранение на телефоне и не облачная синхронизация. Никаких новых внешних
сервисов или API для хранения не используется.

В главном меню появилась кнопка **«📂 Мои чеки»**: дата создания (UTC), общие
расходы с учётом скидки/чаевых, число участников и статус. Список показывает
только чеки текущего пользователя из текущего чата; страницы редактируют одно
сообщение. Открытие чека создаёт новый экран и новую сессию. После этого обычные
кнопки распределения и расчётов редактируют этот экран.

Сохраняются участники, повторяющиеся позиции, назначения, завершённость
распределения, ресторанные оплаты, скидка, чаевые, их плательщик, подтверждение
переводов и исходные структурированные суммы. Статус `completed` означает
именно подтверждённый расчёт переводов; остальные записи — `draft`.
Новая применённая правка сохраняется автоматически. Положительные чаевые
применяются после выбора плательщика; незаконченный ввод остаётся черновиком
только в текущем FSM и не меняет сохранённые суммы.

`/start` открывает главное меню и сбрасывает текущий ввод, но **не удаляет
историю**. Новый чек получает отдельный ID; участники и оплаты не переносятся.
Восстановление проверяет JSON моделями `ReceiptSnapshot`, `ReceiptFacts`,
существующими `ReceiptItem` и `Allocation`. Повреждённая запись не открывается,
остальные доступны. При загрузке не восстанавливаются токены, revision,
выбранные кнопки, message ID или незаконченный ввод. Старые кнопки и сообщения
ввода отвергаются; сумму/имя нужно вводить только в новой активной сессии.

### Конфигурация и структура SQLite

Задайте стабильный путь вне checkout, например в `.env` или окружении:

```dotenv
RECEIPT_DB_PATH=/srv/split-check-bot-data/receipts.sqlite3
```

По умолчанию: `~/.local/share/split-check-bot/receipts.sqlite3`. В контейнере
используйте постоянный volume. Бот создаёт каталог и базу при запуске;
новый файл имеет права `0600`, новый каталог `0700`. Администратор отвечает
за права существующих каталогов/файлов, резервные копии и сохранность volume.
SQLite и её служебные файлы исключены из Git. Содержимое БД не шифруется.

Таблица `receipts`:

| Поле | Назначение |
| --- | --- |
| `id` | Уникальный ID; первая запись идемпотентна по Telegram update |
| `owner_user_id`, `chat_id` | Владелец и чат, проверяются во всех чтениях/записях |
| `created_at`, `updated_at` | UTC ISO 8601 |
| `state` | `allocation` либо `payments` |
| `status` | `draft` либо `completed` |
| `version` | Монотонная версия для compare-and-swap |
| `data_version` | Версия формата снимка (1) |
| `payload` | JSON: `schema_version`, `receipt`, `allocation` |

Деньги и количества в снимке — десятичные строки, без float. `PRAGMA user_version=1`
помечает версию таблиц; неизвестные будущие версии отклоняются, не понижаются.
Лимит — **100 чеков на пользователя во всех чатах, 256 КиБ на снимок**.
При превышении новая запись отклоняется; существующие можно обновлять.
Автоматического удаления истории нет; удаления через интерфейс в этом PR нет.
Телефоны, адреса и прочий сырой OCR, изображения/base64, Telegram file IDs,
секреты и FSM-сессии не входят в снимок. Имена участников и названия блюд
хранятся как необходимые для продолжения работы данные, в логи не выводятся.

### Согласованность экрана, FSM и базы

Обработчик работает с копией FSM под существующей блокировкой aiogram.
После успешного обновления Telegram сохраняется валидированный снимок в
транзакции `BEGIN IMMEDIATE`, затем публикуется FSM. При отказе Telegram
изменение не записывается. Если SQLite отклоняет запись после обновления
экрана, выполняется компенсирующее редактирование прежнего экрана; сумма и
состояние не применяются. Если Telegram отклоняет и компенсацию, ввод денег
отключается, токен меняется; продолжение через `/allocation` или «Мои чеки».
Ошибки показываются без приватных данных; платёжные message/update IDs остаются
использованными при откате, чтобы повтор не применил старую сумму.

Версия снимка проверяется атомарно: разные изменения со старой версией
отклоняются с предложением открыть актуальный чек. Одинаковая повторная запись
не создаёт новую версию. SQL параметризован, операции SQLite выполняются
через `asyncio.to_thread` с коротким ожиданием блокировки (1 секунда).
При временной ошибке запуска инициализация повторяется при следующей операции.

Ограничения: Telegram и SQLite не поддерживают общую транзакцию. При аварийном
завершении процесса между редактированием сообщения и commit восстанавливается
последний успешно записанный снимок; старые кнопки после перезапуска не работают.
Незавершённые шаги ввода/редактор до подтверждения не сохраняются. Чеки прежней
версии бота, жившие только в MemoryStorage, задним числом восстановить нельзя.
Нужен один polling-процесс; несколько копий интерфейса защищены проверкой версии,
но это не совместная многопользовательская работа.

Тесты используют только временную SQLite и подменённый Telegram, без OCR/API:

```bash
python -m unittest tests.test_receipt_store tests.test_config -v
python -m unittest discover -s tests/integration -p test_receipt_persistence_flow.py -v
```
